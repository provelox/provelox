# Changes

What changed in each release, newest first. Security fixes say what was wrong and who could have used it.

## 0.5.0

The first public release of Provelox, tried as release candidates first.

### Open source, and a new image name
- **Provelox is open source**, under the Apache License 2.0. The source is at [github.com/provelox/provelox](https://github.com/provelox/provelox). Issues are welcome; pull requests are not being accepted yet.
- **The image has a new name: `ghcr.io/provelox/provelox`** (it was `ghcr.io/floms/provelox`), and it is public. **A server that runs the old name cannot update itself to 0.5.0**, because an update keeps the image name it is running. Move it once by hand: run `install` from the new image with the same options as the first install (see Install, Upgrading). After that, updates from the console work as before.
- **The image holds the API, the proxy setup and the console.** The `hub` command it once had is gone (the hub has its own image). `install`, `join` and the other commands are unchanged.

### Console
- **Large database dumps move through the server folder too.** The Database card (PostgreSQL, MySQL, MariaDB) gains **Save a backup on the server**, which writes the dump into the import folder (no size limit, nothing through the browser, the app keeps running; "every database on the server" is optional) and shows its path and the `rsync` command to fetch it, and **Restore** becomes a menu: **From a file on the server** (the dumps in the folder with size and age, the `rsync` command to put one there, refresh, delete with confirmation, then add to what is there, or replace it after typing the app's name) or **From my computer** (the upload, which now warns above 200 MB and is not offered above 2 GB). A dump is saved under a hidden name and only appears in the folder when the tool has finished successfully; a failed dump leaves no file. Volume archives and dumps stay apart: a volume's dialog lists only `.tar.gz`/`.tgz` files and a database's only `.dump`/`.sql`/`.sql.gz`. See Guide → Database backup, Moving to a new server.
- **Move large data with rsync, not the browser: the import folder.** **Restore → From a file on the server** lists the archives in `/var/lib/provelox/imports/` (with size, age and free space), shows the `rsync` command to put a file there, and restores the one you pick, with no size limit and no browser in between; the work carries on if the page is closed. **Download → Save a copy on the server** writes a copy of a volume into the same folder (live, or with the app stopped), shows its path and the command to fetch it, and a copy that fails or is cut short (a full disk) leaves nothing behind. The folder's files can be deleted from the dialog. The browser upload now warns above 200 MB and is not offered above 2 GB, and says to use the server folder. New guide: *Moving to a new server*; updated: *Restoring data*, *Downloading data*.
- **Upload and restore an app's data.** Next to Download, Configuration → Storage has **Upload and restore** on every Docker volume: pick a `.tar.gz` (one that Download made, or any gzip tar) and it is extracted into the volume, with a real progress bar and a Cancel. By default only into an empty volume; "Replace what is there" removes everything first and needs the app's name typed, with a red warning and a link to download a copy first. The app is stopped while the data is written and starts again however it ends; owners and permissions are kept. For what looks like a database the dialog says a file-level restore only works if the copy was consistent, and that a dump is safer. Admin sign-in only. See Guide → Restoring data.
- **The summary names what a machine's security check found.** `GET /v1/system/summary` returns `security.findings` (`id`, `severity`, `title`, at most 12) beside the counts, so a monitoring tool can name each finding without the detail, which stays on the machine's own console. The console page says plainly that the check is not exhaustive: a clean result is not proof, and it cannot see operating-system-level or in-memory malware, flaws inside apps, or other machines of a cluster.
- **A download link opened while signed out goes to the sign-in page**, then to the app's Configuration page, instead of showing an error. It never goes straight back to the download address, since a download with "stop the app" would then run just because someone signed in. The sign-in page accepts a `next` address only inside an app's own pages.
- **The security check no longer raises a critical alarm for tools inside an app's container.** A program that runs from a hidden folder (such as Puppeteer's headless Chrome in `~/.cache`) was reported as a sign of malware. A process inside a container is now judged by whether it runs from `/tmp` or was deleted, and is reported as a warning that names the app; the strict rule stays for processes on the machine itself.
- **Security checks.** Settings → Security checks looks for the signs of a server someone else controls: apps that publish a database to the internet, processor work no app accounts for, and (from a read-only helper that sees the host's files) a library forced into every program through `/etc/ld.so.preload`, hidden processes, a second root account, scheduled jobs that run from hidden or temporary places or match known mining malware, SSH password and root logins, the keys that may sign in as root, and Docker open on the network. Findings are listed worst first with what to do, "Check now" takes a new scan, and the Apps page shows an alert when something critical was found. See Guide → Security checks.
- **Back up and restore a database.** For an app running PostgreSQL, MySQL or MariaDB, Configuration → Storage has a Database card: **Download backup** (a dump the database writes itself, consistent while the app keeps running; "every database on the server" is optional) and **Restore from a file…** (add to what is there, or replace it after typing the app's name; a real upload progress bar and Cancel). A dump of another kind of database is refused before anything is touched. The tools run inside the app's own container with its own credentials, which Provelox never sees. Admin sign-in only. See Guide → Database backup.
- **Download an app's data.** Configuration → Storage has a Download button on every Docker volume (also for the services of a project). It saves the volume as one `.tar.gz`, as a real browser download that is streamed and never held. For a running app it asks whether to copy live or stop the app during the copy; for what looks like a database (postgres, mysql, mongo, redis and the like, by image name) it warns that a live copy can be inconsistent and starts from "stop". Admin sign-in only. See Guide → Downloading data.
- **Renaming a service keeps what the old app had.** Renaming a service in a project's compose file used to remove the old app and start a new one, losing its domains, HTTPS settings, password, sign-in, deploy keys and history (only the data survived). The review now notices a service that looks renamed (the only one removed and added, or sharing an image or data mounts) and offers, checked by default, to keep what the old app had; unchecked, it says plainly that the old app goes with its domains. A service with data is briefly unavailable while it moves (and is put back if the new one cannot start); one without data overlaps with no outage.
- **Moving apps into a project lists what they keep.** The review shows each app's addresses (with HTTPS and primary) and the settings made in Networking that carry over, and the generated compose file has a comment under each service saying the same (domains cannot be written in a compose file).
- **Group running apps into a project.** "Move into a project…" in an app's row menu, on the app's own page and on a collection's page (where apps can be ticked and moved together), "Group into a project" for several ticked apps, New → "Group running apps" to pick from a list, or Add → "Apps that already run" on a project's page. Adding to an existing project starts its own services from the values they run with now, so their environment is not blanked. Pick a new project or an existing one, review the generated compose file, and the apps move without being rebuilt: volumes keep their names so data stays, addresses (including the default `<name>.<domain>`) keep working, and the old name stays as an alias. The review says which apps are interrupted: apps with a volume or a published host port restart briefly and move last, all others overlap with no gap. See Guide → Group running apps.
- **Processor has its own tile on Apps.** The fleet summary shows "Memory in use" and "Processor in use" side by side (share of the servers' cores, with the core count), instead of CPU as a footnote under memory.
- **A proper editor for the compose file, and variables grouped by service.** The deploy and update dialog edits the compose file in a YAML editor (colours, line numbers, Tab and Shift-Tab, a Format button, errors marked as you type, `${VARIABLES}` picked out). On wide screens the editor fills the left of the dialog and the variables sit on the right, one folding card per service, with the buttons always in view. "Open project" from the project's own page now closes the dialog.
- **Updating a project shows what will happen.** The review step lists every service as new, unchanged, changing without a restart, or restarting, with the reason (an image, or the names of the environment variables that differ, never their values) and whether the restart interrupts it. A secret that differs from what is running is flagged, so a mistyped key is noticed before it is deployed. A change that cannot be made (a service gaining or losing a volume) is reported in the review, not at deploy.
- **Updates start from the running values.** For any compose file, not only templates, the variables' values are read back from the services (an environment entry, the image, or a word of the command) and fill the update form, so secrets do not have to be retyped. `GET /v1/projects/:name` returns `variables`, and the preview returns `diff`.
- **Upgrade from the badge.** The "newer image" badge on an app is now a button: it asks for confirmation (the image now and after, a warning for a major update or an app with a data volume, a note for an app in a project), deploys the newer image, and reports how it went. A rebuilt tag offers "Redeploy". Images pinned by digest keep the plain badge.
- **Secrets that must be long enough.** A template variable can set `minLength`, and a compose file can declare the same under a top-level `x-provelox: variables:` (`secret`, `minLength`, `label`, `description`). A generated secret is at least that long (never under 32 characters), and a shorter value is refused in the form and again in the preview and deploy. A file that declares nothing still gets a minimum length read from "at least N characters" or "openssl rand -hex N" in a `${VAR:?...}` message. See Guide → Template registries.
- **A deploy that fails part-way can be removed.** A project is saved before its services start, so one whose deploy failed (a mistyped image, say) is a project you can fix and redeploy or remove, instead of leftover services that said "There is no project named…". Removing also cleans up leftovers from earlier failed deploys. The deploy dialog shows each service's progress while the deploy runs, and an image reference containing a space (usually pasted text after the tag) is refused in the preview.
- **Sign in with Google, GitHub or your company.** Networking → Sign in with… on an app: add a provider once (Google, GitHub, or any OpenID Connect provider such as Okta, Microsoft or Keycloak; its redirect address is shown with a copy button), pick it, list the email addresses and domains that may in, and keep chosen paths open. The app is told who signed in (`X-Provelox-Email`, `X-Provelox-User`). See Guide → Sign in with….
- **Behind a CDN.** Networking → CDN on an app: pick CloudFront, Cloudflare, Fastly or add your own (a list of ranges, or an address that serves them), and the proxy keeps the visitor's address instead of the CDN's. The header to read in the app is shown with a copy button. "Only allow requests from the CDN" refuses anyone who reaches the server another way (asks first). Refresh ranges, last-refreshed time and a refresh that failed (the saved ranges stay in use) are shown on the card.
- **Rename an app.** A pencil beside the name. The app restarts under the new name (a short outage) and keeps its data, secrets, deploy keys, usage history and domains. Other apps that name it in their variables can be pointed at the new name, and the old name can stay as an alias.
- **Collections.** What the console called groups are now collections (the API still says groups). A collection's page, `/groups/<id>`, lists its apps in a searchable, sortable table or grid, with rename, delete, add existing app and new app. Breadcrumbs show where an app sits.
- **Projects live with the apps.** The Projects page and sidebar entry are gone; projects are sections of the Apps list, and a project's page uses the same table. Deploying a project no longer creates a group of the same name, and the groups older versions made are removed on start (their apps stay).
- **Add to a project.** An Add menu on a project: a service from a few fields, or a template's services merged into the project's compose file. Names that would clash are renamed, and the change is reviewed like any update before anything runs.
- **Template registries.** Offer your own templates next to the built-in ones from an index file (JSON or YAML) or a git repository on GitHub, GitLab, Bitbucket or Gitea. Templates deploy with the same checks as a pasted compose file.
- **Templates page.** Each template has a logo (or its initials), a one-line description and its category; search, a category list and a registry list sit in one row, with registries in a "⋯" menu. A registry's index can give a template an `icon`: a logo the console has (like `postgresql`) or the https address of a public image (it falls back to initials if it does not load). The registries dialog has copy and download buttons and three examples, including one with variables. A variable a template forgot to declare still gets a field.
- **A little more colour on the figures.** The tiles above the apps list and at the top of an app are tinted by what they mean (green for running, red for a problem, amber for newer images), carry an icon, and draw a bar where a share makes sense.
- **Documentation for template registries**: Guide → Template registries, with every field and a sample index, and the same summary inside the registries dialog.
- **Settings reworked.** Settings is its own area with a grouped list on its left (General, Access, Sources, Infrastructure) and an overview that shows where each thing stands. Each topic is a page of its own: Appearance, Domain & HTTPS, Notifications, Platform pages, Password & tokens, Deploy keys, Image registries, Template registries, Servers, Platform services, Storage & cleanup, Connection. Old addresses redirect. Template registries moved out of a dialog into Settings, with the guide on the page.
- **Template registries can be set from outside.** `PUT /v1/templates/sources/sync` (update scope) adds or updates a registry by its address, and nodes report which registries they read.
- **Deploy keys on the app's Deployments tab.**
- **Searchable selects, one-click theme.** Every select is now a searchable list. The top bar has a one-click light/dark button; Settings → General → Appearance picks System, Light or Dark.
- **Everything about an app in one rail.** On wide screens an app's pages and the sections of the page you are on are listed on the left (Environment, Secrets, Storage, Domains, Ports ...), replacing the row of tabs.
- **Command palette does things.** ⌘K now also runs actions on the page you are on: restart, stop, start, deploy an image, add a domain, variable, secret or deploy key, rename, pin; add a service or template to a project; new app, compose project, template registry; switch theme.
- **Pinned and recent apps** in the sidebar (a star beside an app's name, or in its row menu). Kept in this browser.
- **Registry logins, with logos.** Settings → Registries picks a provider from logos (Docker Hub, GitHub, GitLab, Google Cloud, Amazon ECR, Azure, Quay, DigitalOcean, other), fills in what is always the same (the address, `_json_key`, `AWS`), checks addresses, token shapes and Google key files before anything is sent, refuses duplicates, and keeps the registry's own error in the form.
- **Delete and rename moved** into a "⋯" menu beside Restart on an app. Group and project names on the Apps list open their pages, and one button folds or unfolds every group and project.
- **Fleet summary on Apps.** Running, stopped, needs attention, newer images and current use above the list; each tile narrows the list, and failing apps are linked. Rows show logs, restart and stop/start on hover.

- **Name an app from its domain.** Type or paste a domain (`api.loxti.com`) as the name in New app and the wizard suggests `loxti-api`: the product (the domain's main label) and the role (its subdomain; `web` for the bare domain), picks the collection named for the product when exactly one fits, and attaches the domain when the app is created (HTTPS is turned on later, once its DNS points at the server). Two-part endings such as `co.uk` are understood.
- **Tidy names…** A "⋯" menu on the Apps list proposes the same `<product>-<role>` names for apps you already have, from their first custom domain: it shows each rename (and the collection it would move to), skips apps in a project, without a custom domain, or whose new name would clash, and applies the ticked ones one at a time with the usual rename options (a short restart, other apps pointed at the new name). Nothing is rolled back if one fails.
- **DNS help for a new domain.** After a domain is attached (in the Add domain steps, on the app's Domains section and after creating an app from a domain) the console shows the record to create (a CNAME for a subdomain, A/AAAA for a bare domain, with copy buttons), checks it every few seconds and says whether it is missing, points somewhere else (and where) or is right; when it is right and HTTPS is off it offers Turn on HTTPS.
- **A certificate that does not issue says why, and can be retried.** If a certificate stays pending, the domain row explains the likely reason (HTTPS off, no Let's Encrypt email, DNS missing or elsewhere, or DNS fine but port 80/443 unreachable) and shows what Let's Encrypt said when the proxy's log has it. **Retry certificate** asks the proxy to try again (one a minute and three an hour per address, so Let's Encrypt's failed-validation limit is not hit), with a countdown, and the row follows retrying → issued or failed.
- **Activity.** Settings → Access → Activity lists who changed what and when (deploys, renames, variable and secret changes, domains, collections, tokens), by an admin, an access token or a deploy key, with the outcome. It never stores values: variable and secret values, passwords and tokens are not in it, only names, hosts and image tags. Filter by app, kind of change, who and outcome; `/settings/activity?app=<name>` links to one app. Kept 90 days (`ACTIVITY_RETENTION_DAYS`) up to 50,000 events (`ACTIVITY_MAX_EVENTS`). Admin only.
- **First-run checklist.** An empty instance's Apps page lists the first steps (platform domain, first app, deploy, deploy key), each linking to the right place and ticking itself; it can be hidden.
- **Keyboard shortcuts.** `g a`, `g t`, `g s` go to Apps, Templates and Settings, `n` starts a new app, `/` searches, `?` lists them; the command palette shows the keys.
- **Deleting asks for the name.** Deleting an app or a collection, or removing a project, lists what goes and what stays and enables the button only once the name is typed.
- **Works on a phone.** No sideways scrolling on the pages checked at 390 px, stacked card headers, and 40–44 px touch targets on touch screens (desktop unchanged).
- **Accessibility.** Light-mode buttons use a slightly darker blue so their text meets the contrast minimum (dark mode keeps the bright blue with dark text), and automated axe checks now run on the main pages in light and dark.
- **A lighter Apps list on large instances.** Rows no longer all redraw on every poll or keystroke, the usage poll is compressed, and dialogs load when first opened. At 1,000 apps the list shows about a third sooner (745 → 490 ms), uses 45% less memory (108 → 61 MB) and idles on a third of the CPU and a fifth of the traffic.

### API
- **Database dumps through the import folder.** `POST /v1/apps/:name/database/export[?all=1]` runs the dump (`pg_dump -Fc`, `pg_dumpall`, or gzipped `mysqldump`/`mariadb-dump`) and writes it into the import folder as `<app>-<time>.dump` or `.sql.gz`: first as a hidden `.part` file, moved into place only after the tool exited 0, and removed on any failure or abort, so a half dump is never listed; answers `{file, sizeBytes, dir}`. `POST /v1/apps/:name/database/restore?from=<file>` (no body; a body together with `from` is 400) restores a dump that is in the folder, with the same `clean=1&confirm=<app>` rule and the same format detection as the streamed restore: a dump of another engine is refused before the tool starts, a file that stops being readable half way is reported (422), and the folder is only ever mounted read-only for it. The import folder now holds two kinds of file, told by name in one place: `.tar.gz`/`.tgz` are volume archives and `.dump`/`.sql`/`.sql.gz` are database dumps. A volume restore refuses a dump name and a database restore refuses an archive name (400), and `GET /v1/system/imports` gives each file a `kind` (`volume` or `database`). Admin only; activity events `database.export` and `database.restore` (with the file name) without content.
- **Import folder.** `GET /v1/system/imports` lists the archives in the import folder (`{dir, files: [{name, sizeBytes, modifiedAt, gzip}], freeBytes}`) and `DELETE /v1/system/imports/:file?confirm=<file>` removes one (admin only). `POST /v1/apps/:name/volumes/:volume/restore?from=<file>` (no body) restores from a file in the folder, with the same `replace`/`confirm` rules and the same stop and start of the app as an upload; `POST /v1/apps/:name/volumes/:volume/export[?stop=1]` saves a copy of a volume into the folder as `<app>-<volume>-<time>.tar.gz`, hidden until it is complete and read back whole. The folder is `IMPORTS_DIR` (default `/var/lib/provelox/imports`, a path on the server, set to mode 0700): only that folder is ever touched, only by short-lived helper containers, and a file is only ever named (letters, digits and `. _ -`, ending `.tar.gz` or `.tgz`, no slash or `..`), then looked up in what the folder holds; links and folders are never listed. The scripts the helpers run take the name as an argument and check it again. The API's request timeout is back to the framework default (the six hours the browser upload had raised it to are gone: the proxy's 60-second limit decides what a browser upload can do, and the server folder has no such limit).
- **`POST /v1/apps/:name/volumes/:volume/restore`** (admin) puts the request body, a `.tar.gz`, into one of the app's named volumes. It is streamed into a short-lived helper that can write only that volume (no network, read-only system, memory and process limits, and only the permissions to give files their owners and modes), never held in memory. Into an empty volume by default (a volume with files answers 409); `?replace=1&confirm=<app name>` empties it first. The app is stopped while data is written and started again with its instances however it ends. A body that is not gzip is refused (400) before anything is stopped; a volume the app does not have is 404, a hub-managed app, several instances, or another machine's volume 409. Recorded as `volume.restore` in the activity log, never with content. See Guide → Restoring data.
- **Database dump and restore.** `GET /v1/apps/:name/database` says which engine an app runs and whether it can be backed up; `GET /v1/apps/:name/database/dump[?all=1]` streams a dump (`pg_dump -Fc`, `pg_dumpall`, or gzipped `mysqldump`/`mariadb-dump`) and cuts the connection if the tool dies half way; `POST /v1/apps/:name/database/restore[?clean=1&confirm=<app>]` streams a dump into `pg_restore`, `psql`, `mysql` or `mariadb` (format detected from the first bytes, a dump of another engine refused with 400; `clean` needs the app's name, 400 otherwise). The tools run through a fixed script inside the running container (`docker exec`), reading the container's own environment including `*_FILE`; no secret is on a command line. Admin only; activity events `database.dump` and `database.restore` without content. Only apps on the machine the API runs on.
- **`GET /v1/system/security`** (admin) returns what the security check found (`?fresh=1` for a new scan, `?cached=1` to only read the last). A scan runs 90 seconds after the API starts and every 30 minutes, and `GET /v1/system/summary` carries `security: {critical, warning, at}` from the last one, which a monitoring tool can read to mark an instance critical. The host is read by a helper container with no network, a read-only filesystem and two added permissions (reading any file, and seeing what program another process runs); nothing is changed.
- **Download a volume.** `GET /v1/apps/:name/volumes/:volume/download` (administrator only) streams the named volume as `application/gzip`, with `Content-Disposition: attachment`. The volume is looked up in the app's own definition by the name the app gives it (never a Docker name, and never a server directory, which is refused with the reason); it is read by a helper with the volume mounted read-only, no network, no privileges beyond reading any file, a read-only filesystem and a memory cap. `?stop=1` stops the app while it is copied and starts it again however the copy ends, including when the client leaves; a hub-managed app or one with several instances is refused. A volume held to another machine of the cluster answers 409 saying which. A copy that dies half way cuts the connection instead of ending the file. Each download is an event in the activity log (what was taken, never its content).
- **The host reading says how much the processor really works.** `GET /v1/system/summary` now returns `host.cpuBusyPercent` (share of the processor doing work since the last reading) and `host.stalledPercent` (`{cpu, io}`: how much of the last minute something had to wait, from the kernel's pressure figures). The load warning is also held back for the first 20 minutes after a machine starts, since the average then still carries the start itself.
- **Deploys no longer drop requests.** The proxy found out about a new container only every 15 seconds, so for that long after a deploy a few requests went to the container that had just stopped and failed or hung (one waited the full 40 seconds in a test). It now checks every 2 seconds; six redeploys of a web app under constant load lost none. Apps that keep data still stop before their replacement starts, so they have a short gap on every deploy by design.
- **Renames in a project.** Deploy and preview take `renames` (`{"<new service>": "<old service>"}`): the old app becomes the new one through the same machinery as moving an app in, keeping its domains, primary domain, HTTPS and redirect settings, password, sign-in, CDN settings, deploy keys, usage history and the old name as an alias. The preview returns `renameCandidates` (suggestions only, never applied without `renames`), `renaming`, and `keeps` (addresses and settings kept) for apps moving in or being renamed; the deploy returns `renamed`.
- **Updating a project no longer resets password, CDN, sign-in, error pages, linked domain or placement** that were set on a service in Networking or Settings. Only the addresses and a few other settings were kept before; a redeploy of the compose file dropped the rest.
- **Grouping running apps.** `POST /v1/projects/from-apps` and `POST /v1/projects/:name/add-apps` (`{"apps": [...]}`) build the compose file for apps that already run; the project preview returns `adopting` and the deploy takes `adopt`. A moving app with no volume or host port is started in its new place (not yet routed) and waited for before the old one is removed; one with data stops first and is restored if the new one fails to start. Apps using Docker secrets or host-directory mounts are refused with the reason.
- **Pre-release numbers are compared as numbers.** `0.5.0-rc.10` was treated as older than `0.5.0-rc.8` (the tag after the dash was compared as text), so the platform refused to update from rc.8 to rc.10 ("older than the … that is running"). Both now follow semver: `rc.8`, `rc.9`, `rc.10`. Only release candidates were affected.
- **`detach` and `uninstall` commands.** `detach` makes apps independent of the API (it removes the error-page step from their routes, labels only, nothing restarts), so the API can go while the apps keep answering. `uninstall` removes Provelox without disturbing the apps: it runs `detach` and removes only the console and API. `--remove-apps` also stops and removes the apps, the proxy, the platform's own secrets and networks (volumes and apps' secrets stay unless `--delete-data`, which only goes with `--remove-apps`) (Provelox cannot read a secret back, so deleting one is not undoable). Both show a plan and change nothing without `--yes`, touch only objects with Provelox's label, and never leave the Swarm. With `--remove-apps` it lists the apps that will stop and marks ones on a tag that can move (they may come back as a newer image), and `install` waits out Docker's slow removal of the old network instead of failing. See Guide → Removing Provelox.
- **Compose files can declare variables.** A top-level `x-provelox: variables:` (`secret`, `minLength`, `label`, `description`, `default`) is read by the preview and the deploy: a value shorter than its `minLength` is refused, and a bad declaration is reported. An image reference containing a space is refused in the preview. `DELETE` of a project also removes the leftovers of a deploy that failed part-way (it used to answer "no project").
- **Sign in with an identity provider.** An app can set `sso: {provider, emails, domains, openPaths}`. The proxy asks the API about every request (forward auth); the API answers from a sealed cookie and tells the app who signed in. Providers are `google`, `github` and `oidc`, kept at `/v1/sso` (client secrets sealed, never returned). One redirect address (`API_PUBLIC_URL`) serves every app and domain. An app that asks for sign-in while it is unavailable is not served rather than served open. `SSO_SESSION_HOURS` (default 12), `SSO_VERIFY_URL`.
- `POST /v1/apps/:name/rename`, `GET /v1/apps/:name/references`.
- `GET|POST /v1/templates/sources`, `POST /v1/templates/sources/:id/refresh`, `DELETE /v1/templates/sources/:id`.
- `POST /v1/projects/:name/add-service`, `POST /v1/projects/:name/add-template`.
- `GET /v1/apps/:name/domains/:host/diagnosis`, `POST /v1/apps/:name/domains/:host/retry-certificate` (admin).
- `GET /v1/activity` (admin).
- **Apps behind a CDN.** `PATCH /v1/apps/:name {"cdn": {"provider", "enforce"}}` says which CDN sits in front of an app. The proxy then keeps the CDN's `X-Forwarded-For` (so the visitor's address survives instead of being replaced by the CDN's edge address), and with `enforce` it answers only requests from the CDN's address ranges, so the app cannot be reached around it. Amazon CloudFront, Cloudflare and Fastly are built in; `PUT|DELETE /v1/cdn/providers/:id` adds any other from a list of ranges or an address to fetch them from. Ranges are refreshed every `CDN_REFRESH_HOURS` (6; 0 turns it off) and on `POST /v1/cdn/refresh`; a failed or suspicious refresh keeps the last good ranges. `GET /v1/cdn` lists them. A change in the ranges the proxy trusts restarts it briefly. `PROXY_TRUSTED_IPS` trusts extra ranges by hand.
- Docs: new *Domains and HTTPS* guide.

### Security: Next.js and two API dependencies updated
- **What was wrong.** The console runs on Next.js 16.4.0, which had published advisories for versions 16.0.0 to 16.4.0: remote code execution in the image optimizer when SVG files are used, a denial of service in the App Router through server actions, and remote code execution in `use cache` functions that return typed arrays. The advisories describe attacks from anyone who can reach the console address; we did not test which of them apply before sign-in.
- **What changed.** The console is on Next.js 16.4.3. Its image optimizer is also switched off (the only image it shows is already served as is), so that endpoint is gone. In the API, `body-parser` is updated and `multer` is held at 2.5.0 (the API takes no file uploads, so it was not reachable). A remaining advisory in zod 3.x (memory use when checking very large arrays) is not fixed here: every collection the console checks has a size limit, and the fix is a major version. It is tracked for its own change.

### Image and releases
- **A smaller image.** The image optimizer's native libraries, other platforms' SQLite binaries, source maps and type files are left out, and identical files are stored once. Behaviour is unchanged (checked against the previous image: the same console responses, the same command help).
- **Faster release builds.** Each CPU family now builds on its own kind of machine (the Arm build no longer runs under emulation) with a build cache, and the two are joined into one multi-platform image under the same tags.
- **Dependabot** opens weekly update pull requests for the API, console, docs and the GitHub Actions the workflows use, with minor and patch updates grouped.

## 0.4.0

### Security fix: operate tokens could read environment values
- **What was wrong.** Restarting, starting, stopping, reconciling or deploying an app with an access token at the *operate* level (the level a monitoring tool uses) answered with the app's whole definition, including the **values of its environment variables**. Anyone holding such a token could read secrets such as database passwords. Read tokens were not affected, and neither were signed-in admins, who may see them.
- **What changed.** Those answers now carry only the app's name, image, instance count, status and addresses when the caller is a token. A test sets a secret variable and checks every operate action's answer. If a script or monitoring tool holds an operate token, treat the variables of the apps it can reach as seen, and rotate any that matter.

### Newer images
- Provelox asks the registry each app's image came from whether there is a **higher version tag** (major, minor, patch or newer, comparing only tags of the same shape, so `1.4.0-alpine` is compared with other `-alpine` tags and a release candidate never stands in for a release) or a **rebuilt tag** (the registry now holds another build under the same name). It reads only metadata, with the sign-in already saved under Registries, and never pulls an image.
- Answers are cached for 6 hours (30 minutes after a failure), kept through a restart, and refreshed behind the request, so a page never waits for a registry and reloading it asks nothing.
- Shown as a badge in the console's apps list and on an app's overview, with a *Check now* button. Bare major lines such as `mysql:8` only get rebuild detection.

### API
- New routes: `GET /v1/system/processes` (operate), `GET /v1/system/storage/summary` (read), `POST /v1/system/storage/images/prune-unused` (update), `GET /v1/system/image-updates` (read), `POST /v1/system/image-updates/check` (operate), `GET /v1/apps/:name/versions` (read), `GET /v1/apps/:name/config` (read) and `POST /v1/apps/:name/scale` (operate).

## 0.3.3

### Password protection for apps (HTTP basic auth)
- **Networking → Password protection**: ask for a username and password before an app, at every address it has, done by the proxy so it works for any app. Several users; passwords are stored only as hashes (bcrypt) and shown once when generated; a password can be generated; chosen paths (a webhook, a health check) can stay open without one. Turning it on or off applies at once and does not restart the app.
- **Migration from CapRover keeps it.** CapRover's HTTP basic auth was silently dropped by the import, which left a protected app open to the internet. It is now carried over (its hash, or its password hashed on Provelox). When the password cannot be read, the app is created stopped, with a warning, so it is never reachable without the password it had.

### Migration that survives a dropped connection
- A copy of a large volume now prints a line every 15 seconds saying it is still going and for how long, instead of nothing for many minutes.
- Everything the wizard prints is also written, with the time, to `provelox-migration.log` (`--log-file`), so a dropped SSH session does not lose it. The wizard says at the start to run it in `tmux` or `screen`, and that running it again carries on.
- The copy helper image is made available before anything is created, with a 10 minute limit and a message saying what to do (`--helper-image`), instead of waiting silently on a pull that never ends. Calls to the API have a 5 minute limit with a message that says to run the command again.
- A helper container left behind by a cut-off run is removed before the next copy, so it cannot go on writing to a volume that is about to be emptied. The helper's log is read only from its end (a comparison of a big live volume can list a great many files).
- The API logs a line for every refused request (method, path, status, message; never the body), which it did not before.

## 0.3.0

### Environment variables and names
- **Bulk environment editing**: the app's Configuration tab can edit its variables as text (`NAME=value` per line), import a pasted `.env` file or JSON object, or choose a file, with a preview of what is added, changed and removed (merge, or replace everything) before anything is saved; and copy them all as `.env`. Quoted and multi-line values (a private key, say) are read and written correctly.
- **Other names**: the Networking tab can add and remove extra internal names for an app, such as the `srv-captain--name` an app moved from CapRover keeps so its neighbours still find it.

### Migration from CapRover
- The check that stops an app using the platform's own address now reads where the console and API are actually served, so an app can keep `api.<root>` when the platform lives elsewhere. Before, such an app was refused and the whole import step for it failed, leaving it without its environment, aliases and domains.
- An app an import could not finish is removed so running the import again redoes it, and an app left half-made by an earlier run (no CapRover name) is finished instead of skipped.

### Clustering
- **Servers**: Settings → Infrastructure → Servers lists every server of the cluster with what runs on it. **Add a server** shows the command to run on the new server (worker or manager) with the manager's address and the new server's own address as editable fields, and watches for the server to join. No password or SSH key is shared.
- **Node controls**: pause, drain, activate, make a manager or a worker, remove from cluster. Each says what will happen first. Guards refuse demoting the server the API talks to, demoting the last manager that is up, draining or pausing the only manager that can take work, and removing a server that has not left or that holds an app's data.
- **Where an app runs**: any server, workers only, managers only, or one server. An app with local data is held to the server that has the volume (pinned by server id), is pinned as soon as a second server joins, and can be released when that server is gone.
- **Encrypted network**: the network apps talk over is created encrypted. For earlier installs the Servers page warns once there are two servers and shows `encrypt-network`, which is safe to run again if interrupted.
- New commands `join` and `encrypt-network`; new guide *Servers and clusters* (ports, firewall rules, private networks).

### Security (second review)
- Cluster: pins can no longer land on the wrong server or be taken by a server that reuses a name; a Docker error stops an apply instead of letting an app run unconstrained; removing a server follows Docker's real rules.
- An app can no longer be created with a default address that is the platform's own (`api.<root>`, `console.<root>`), which an update token could do through a blueprint.
- CI deploy keys can no longer deploy a different image than the one the app runs (the first deploy may name it).
- Host ports 22, 80, 443, 2375, 2376, 2377, 4789 and 7946 cannot be published on any path, including Compose files.
- Bind mounts of `/./etc` and similar no longer bypass the host-path acknowledgement; `/var/lib/containerd` and `/var/lib/kubelet` are covered.
- The placeholder page is sent with a real Content-Security-Policy header; webhook checks follow what a name resolves to.
- The public error-page address no longer reveals which apps exist; bad request bodies return 400 or 413 instead of 500 with a stack trace.
- Failed-login tables are bounded; compose variable substitution rejects very long values.
- Console: the visitor's address is passed to the API so one person's wrong passwords no longer lock everyone out (`CONSOLE_TRUST_PROXY`); removed an unused dependency.
- CI: the external end-to-end job no longer uploads traces that could contain the instance password.
- Docs: new *Security* page; what each token level can do is stated accurately.
